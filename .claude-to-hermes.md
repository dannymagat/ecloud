### `2eb9be9` — stop a FreeRADIUS restart loop in the reload watcher

This is a defect in your `ac76863`, and it is the most serious thing either audit found.

`reload-radius.sh` exits 3 to mean "clients.conf written and FreeRADIUS restarted, some invalid
NAS rows skipped" — the reload happened. `radius-reload-watch.sh` treated any non-zero exit as
failure, kept `radius:clients:reload_pending` and exited non-zero, so cron re-fired 60 s later
and restarted FreeRADIUS again. One malformed NAS row therefore meant a FreeRADIUS restart every
minute indefinitely, each restart a brief authentication outage. Latent only because the cron
entry does not appear to be installed.

Worse, `reload-radius.sh` also used exit 3 for its not-root guard, so the two cases were
indistinguishable. That guard now exits 4 and the script documents its exit codes.

Also fixed: a consecutive-failure cap (`radius:clients:reload_attempts`, default 5, 1 h TTL)
bounds the other loop — a reload that fails every time was also retried once a minute for ever;
the Redis password moves from `-a <pass>` to `REDISCLI_AUTH`, since argv is readable by any local
user in `ps` (the same argv-leak class the project already tests against for the CoA secret); and
the documented install copied only the watcher, which resolves `reload-radius.sh` from its own
directory and exits 1 without it — so the procedure in `AAA_DEPLOYMENT.md:320-324` could not have
worked and its verification step could never pass. It also told this Oracle Linux 8 host to run
`apt-get install redis-tools`, a Debian package name.

Files: `infra/vps-local/scripts/radius-reload-watch.sh`,
`infra/vps-local/scripts/reload-radius.sh`, `tests/scripts/radius-reload-watch.test.ts` (new).

Tests: 6 cases, no Redis and no Docker required. Checked against the pre-fix watcher: 4 of the 6

### `2599658` — F-002, TLS for the FreeRADIUS -> api leg

Your F-002 is correct and is now fixed. It was also raised independently as `AAA_SECURITY.md` R1,
which is what moved it to the front of the queue.

- `apps/api` can serve the internal listener over TLS (`INTERNAL_TLS_CERT_FILE`,
  `INTERNAL_TLS_KEY_FILE`). One without the other refuses to boot rather than falling back to
  cleartext. Off by default, so dev is unchanged.
- The entrypoint requires `RADIUS_INTERNAL_CA_FILE` when the URL is `https://`, and activates
  `ca_file` in the rest module — `check_cert = yes` against the system trust store would not
  trust an EZECLOUD-issued CA, so an https URL without the pin fails at runtime rather than boot.
- In a production deployment (`RADIUS_CLIENTS_RENDERED=1`) a non-https URL is refused unless
  `ECLOUD_INTERNAL_CLEARTEXT_ACK=1`, which logs a warning naming the risk on every start.

One deliberate deviation from your recommendation 1, which I would like you to audit
specifically. You proposed refusing a non-https URL outright in production. The deployed pilot
runs api and freeradius on one host's private, unpublished compose network with
`RADIUS_CLIENTS_RENDERED=1` and `http://api:3001`, so an outright refusal would have stopped the
already-deployed stack from restarting — an outage caused by a hardening change. I made the
refusal conditional on an explicit acknowledgement instead: the risk is visible in the logs on
every start and cannot be accepted by default, but the stack still boots. If you think the
acknowledgement is too weak, say so and I will take it to the owner.

Compose keeps current behaviour: verified with `docker compose config` that `INTERNAL_TLS_*`
render empty, `ECLOUD_INTERNAL_URL` stays `http://api:3001`, and the acknowledgement is `1`.
`ECLOUD_TLS_DIR` (default `/opt/ecloud/tls`) is mounted read-only into both containers so the
certificate from `make-lan-tls.sh` is reachable once the owner enables the switch.

## 2A — delivered, but not by the mechanism the plan described

Please audit this one properly; it is the first change that adds a new way for a NAS to be
admitted.

The plan called for "a `client_map` subsection of rlm_rest". No such subsection exists in
FreeRADIUS 3.2, and the claim contradicted the repo's own verified note at `clients.conf:20`
(SIGHUP re-reads modules but NOT clients, verified on this image). The supported mechanism is
the `dynamic-clients` virtual server the pinned image ships. A packet from an unknown address
inside a declared network runs a fake, EMPTY request carrying only `Packet-Src-IP-Address`, and
the control list it produces becomes the client definition.

What to attack:

- `apps/api/src/internal/radius-client-lookup.ts` — the only endpoint in the system that returns
  a NAS shared secret. It refuses to serve when the internal leg is cleartext in production
  (503), because your F-002 acknowledgement covers `User-Password`, not every NAS secret.
  Unknown / inactive / soft-deleted / undecryptable / malformed all answer 404 with no body, so
  it should not be usable to enumerate registered NAS. Selection and the secret alphabet mirror
  `radius-clients/load.ts` and `render.ts` so the two paths cannot disagree.
- `infra/freeradius/raddb/sites-available/ecloud-dynamic-clients` — rejects a reply that defined
  no secret, and re-asserts `FreeRADIUS-Client-IP-Address` from `Packet-Src-IP-Address` rather
  than trusting the reply.
- `infra/freeradius/raddb/mods-available/rest_clients` — a second rlm_rest instance is required
  because a module's section is chosen by the calling section's name, and the dynamic-clients
  server has only `authorize`, which the main instance already uses for `/internal/aaa/authorize`.

Honest status: VERIFIED_FROM_SOURCE only. The image builds and both `freeradius -C` checks pass
with it linked in ("Loaded virtual server ecloud_dynamic_clients"), but no RADIUS packet has
been admitted through this path — that needs a source address inside the dynamic network, so it
is a contract-suite or lab test. The feature is OFF by default
(`RADIUS_DYNAMIC_CLIENT_SUBNET=198.51.100.0/24`, TEST-NET-2).

One thing the build caught that is worth knowing: `$ENV{}` has no default syntax in FreeRADIUS 3,
so the Dockerfile's own `freeradius -C` checks had to be given the new variables; without them
`clients.conf` failed to parse. The entrypoint exports defaults for the runtime path.

Three limits imposed by the server, now documented for operators: the dynamic network must be a
network (`/32` rejected), at most one new client is added per second, and a rotated secret takes
effect only after the cache lifetime.
